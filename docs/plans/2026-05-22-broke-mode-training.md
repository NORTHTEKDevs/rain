# Broke-Mode RAIN Training Strategy

> **Goal:** make RAIN as intelligent as possible without spending the $20-50k
> figure from the funding plan. Lean on the workstation that's already on
> the desk, the local LLMs already installed, and a handful of free-tier
> cloud accounts. Save real money for v1.0 fundraising.

Status: drafted 2026-05-22 after confirming the Corsair AI Workstation 300
(Ryzen AI MAX+ 395 + Radeon 8060S iGPU + 128 GB unified RAM) can train RAIN
locally via PyTorch + DirectML.

## What "training like an LLM" actually means for RAIN

RAIN's architecture intentionally does NOT train like an LLM. The pitch is:
LLMs need $100M GPU clusters because they re-fit billions of weights on
every token of training data. RAIN front-loads a small bootstrap pretrain
and then learns continuously from interaction with no global gradient. So
the question "can we make RAIN LLM-quality without LLM money" decomposes
into four sub-questions, three of which have zero-marginal-cost answers.

| Capability source | LLM path | RAIN broke-mode path | Cost |
|---|---|---|---|
| World knowledge | parameters baked in during pretrain | KB seed from local-Ollama teacher | $0 |
| Reasoning ability | parameters + chain-of-thought prompting | Tsetlin clauses + multi-hop KB inference + think-aloud | $0 |
| Language fluency | massive next-token pretrain | HYMN bootstrap pretrain on local hardware | $0 - $200 |
| Calibration / ToM / transparency | post-hoc instruction tuning + RLHF | already structural in RCK-sourced modules | $0 |

Three of four columns cost nothing on the workstation. The one that costs
something (language fluency) is exactly where the local hardware is most
useful: the iGPU + 96 GB unified VRAM can train HYMN at v0.5 scale without
renting anything.

## The four-track broke-mode plan

### Track 1 -- HYMN bootstrap pretrain on the iGPU

**Goal:** produce a Phase-1 HYMN checkpoint that clears the Tier-2 L1
threshold (currently 0.5 HV-MSE; later 1.55 nats/char NLL) on Tiny
Shakespeare and then WikiText-2.

What's done:
- `scripts/pretrain_hymn.py` runs end-to-end in pure numpy (CPU only).
  First real run: 5000 steps, dim=512, hidden=256, 6 seconds wall clock,
  loss 1.232 -> 0.988.
- L1 benchmark consumes the produced checkpoint and reports a real number.

What's needed:
1. **Port `HymnSurrogate` to PyTorch** so the training loop runs on the iGPU
   via DirectML. Estimated 1-2 days. Target throughput: 5-10x current
   numpy speed for the same architecture.
2. **Add sequence context.** Current input is `np.zeros` -- the model only
   sees the current char. Wire in prior-K hypervectors as the `input_`
   argument (bundling them with `bind`). Big quality lever.
3. **Add real cross-entropy loss.** Project HYMN output back to vocab via
   nearest-codebook-vector softmax, compute NLL. Replaces MSE-on-HV.
4. **Adam optimizer** instead of plain SGD. Standard for transformer
   training; HYMN should inherit the better convergence.
5. **Longer runs.** 50K-500K steps on Tiny Shakespeare (minutes-to-hours on
   DirectML). Then 1M+ steps on WikiText-2 (a few hours on DirectML).

Estimated dollar cost: **$0.** All on-device.

### Track 2 -- Knowledge distillation from local Ollama LLMs

**Goal:** simulate the "world knowledge" baked into a frontier LLM by
loading RAIN's KB with millions of facts generated by local Ollama models.

The qwen3-coder-30B model running locally on this workstation can produce
~50-200 tokens/sec via Ollama. That's enough to generate millions of
structured facts per day at zero marginal cost. Concretely:

- **KB seeding pipeline (new):**
  - Prompt template: "Output 100 (subject, relation, object) triples
    about <topic>. JSON only."
  - Topics: 10K Wikipedia categories, scraped offline.
  - Throughput: ~10K-50K triples/hour with qwen3-coder-30B on the 8060S.
  - Target: 1-10 M facts in the KB. Compare to LLaMA-3-8B's ~250B parameters
    (most of which encode similar factual knowledge); RAIN's KB queries are
    O(1) shard lookups, no parameter cost.
  - Quality control: small Llama-3.2-3B model rates each triple, drops
    triples with confidence < threshold.
- **Synthetic dialogues for cognitive grounding:** generate 10K-100K
  Sally-Anne ToM variants, SCAN compositional examples, multi-hop
  reasoning dialogues. All offline, $0.

Estimated dollar cost: **$0.** Time cost: a few overnight runs.

### Track 3 -- LLM-as-judge for continual learning + RLAIF-style feedback

**Goal:** use local Ollama models as eval judges during Phase 2 continual
training. Replaces human RLHF labels with free LLM-generated labels.

- For every RAIN response, ask `devstral-24B` whether it's
  (a) correct, (b) calibrated, (c) on-topic.
- Feed the verdict back as `agent.feedback(...)` updating the
  per-relation Bayesian calibration tally.
- This is the closest local equivalent to the "RLAIF" technique that
  Anthropic + others use for post-training instruction tuning.

Estimated dollar cost: **$0.** Time cost: built into Phase 2 runtime.

### Track 4 -- Free-tier cloud GPU when local hits scaling ceiling

When local DirectML can't hold the training run any more (probably during
v0.5 -> v1.0 transition with WikiText-2 or larger), fall back to free
cloud GPU. In rough order of credit + ease:

1. **Kaggle Notebooks.** Free T4 x2 (30 GB VRAM) or P100 (16 GB). 30 hours
   GPU/week with persistent storage. The least-friction option for short
   pretrains.
2. **Google Colab free tier.** Free T4 (15 GB VRAM). ~12 hrs/day usage cap.
   Good for one-off experiments; less reliable for multi-hour pretrains.
3. **HuggingFace Spaces (zero-GPU).** Free A10G for inference; training is
   limited.
4. **Lightning AI free tier.** ~22 free GPU credits/month (small but real).
5. **Modal.com starter credit.** $30 free credit on signup.
6. **RunPod community pricing.** $0.20-0.40/hr for spot A4000/A5000. Only
   when the above are exhausted.

Strategy: keep a working training run in TWO places. Local DirectML for
fast iteration (5 seconds per 5K steps). Kaggle T4 for overnight runs of
WikiText-2-scale work (free, 30 hours/week, more VRAM).

Estimated dollar cost: **$0 - $50** if RunPod gets invoked late.

## Concrete next steps (ordered)

1. **Land this doc + the first real Tiny Shakespeare pretrain in a commit.**
   Establishes the broke-mode baseline that future work measures against.
2. **Port `HymnSurrogate` to a PyTorch module.** Same forward and backward
   semantics; same checkpoint format; just runs on DirectML when available
   and CPU otherwise.
3. **Add sequence context to the trainer.** This is THE single biggest
   quality lever for Tier-2 L1. Target: HV-MSE below 0.5 on Tiny
   Shakespeare with sequence-context=16.
4. **Pipe Ollama-as-teacher into `scripts/seed_kb_from_ollama.py`.**
   Generate the first 100K triples. Measure how N1 retention + N5
   transparency move when the KB is rich.
5. **Replace MSE-on-HV with real NLL via nearest-codebook softmax.**
   This is the Phase 2.3 work referenced throughout the implementation
   plan. After this lands, the L1 0.5-MSE threshold gets replaced with the
   real 1.55 nats/char target.
6. **Run the full Tier-1/2/3 sweep on the trained checkpoint.** Re-execute
   N1 (retention), N2 (ECE), N5 (citation coverage), L1 (Tiny Shakespeare),
   A2 (SOFAR ablation -- now with trained LoRA weights, so the 3%
   improvement threshold becomes a real test).
7. **Decide WSL2 + ROCm.** Only if DirectML hits a perf or feature
   ceiling. WSL2 install takes a few hours and a reboot; current DirectML
   throughput is enough for v0 work.

## Anti-goals

- **No paid Claude API for training data generation.** Local Ollama is
  more than sufficient for the KB seed + judge tracks; Claude Max should
  be saved for design, code, and review work where its quality matters.
- **No cloud GPU before local is saturated.** A 4090 rental at $0.40/hr
  feels cheap until you leave it running for a week. Default to the
  iGPU; only escalate when measured throughput is unblocking real progress.
- **No `transformers` library inside the inference path.** RAIN's whole
  pitch is no-LLM-in-the-loop. We use HuggingFace models OFFLINE to seed
  the KB and judge outputs, but the runtime path stays clean.
